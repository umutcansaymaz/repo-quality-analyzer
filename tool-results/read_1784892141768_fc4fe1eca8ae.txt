   196→[CRITICAL] AUDIT-1 #1 — GitHub token persisted to disk in cached clone's .git/config
   197→File: src/repo_analyzer/adapters/vcs/github_provider.py:128
   198→      src/repo_analyzer/adapters/vcs/clone_service.py:106,119-133
   199→Evidence:
   200→  github_provider.py:128 -> return f"https://x-access-token:{token}@{repository.host}/{repository.owner}/{repository.name}.git"
   201→  clone_service.py:106  -> dest = self._cache_workspace_path(cache_key)   # cache_dir/clones/<sha256[:16]>
   202→  clone_service.py:111  -> self._clone_with_retry(provider, resolved, dest, ...)
   203→  clone_service.py:119  -> if use_cache: self._cache.put(entry)            # registers in SQLite + leaves files on disk
   204→Impact: `git clone https://x-access-token:ghp_xxx@github.com/...` writes the bearer URL into `.git/config` (remote "origin" url field) AND `git ls-remote` may write it into `.git/refs/` pack files. CloneService caches the working tree at `~/.cache/repo-analyzer/clones/<hash>` with default umask (typically 0755 dirs / 0644 files). Any local user can `cat cache_dir/clones/*/​.git/config` and extract the GitHub PAT. The token also survives in SQLite cache_entry rows (workspace_path + repository_url columns) and is never scrubbed on cleanup_workspace().
   205→Credentials leak: YES — PAT leaked to filesystem, world-readable by default.
   206→Subprocess safe: arg-list form is safe from shell injection, but the credential-in-URL pattern is the leak.
   207→Fix: Use `git -c credential.helper=` clone with the token supplied via `GIT_ASKPASS` env or `http.https://github.com/.extraheader=AUTHORIZATION: basic <b64>` config (git's recommended pattern), never embed in the URL. After clone, run `git remote set-url origin https://github.com/owner/repo.git` to strip credentials from .git/config. Restrict cache dir to 0700.
